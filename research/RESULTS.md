# RecruitSmart research pipeline — run log and results

Generated by actually running every script in this folder against the
current codebase. This is the "did it run, and what did it print" record
-- read it alongside the honesty caveat in every section below before
putting any number in a paper.

**Dataset used for this run: `research/data/` as shipped in this
package -- i.e. the synthetic dataset from `generate_synthetic_dataset.py`
(30 resumes x 10 jobs, labels.csv relevance judgements). These are NOT
real human-annotated labels** -- `research/data/dataset_metadata.json`
records this, and every script below prints a loud provenance banner
confirming it at the top of its output. Every table here demonstrates the
pipeline is wired correctly end-to-end; none of it is citable until
`labels.csv` holds real human annotations (see section 7).

**Correctness fix applied since the previous run**: `matching_lib.py`'s
`hybrid_recruitsmart_score()` used to add `+ ontology_score * 0.05` into
`overall`. The live app (`app/utils/ai_parser.match_resume_to_job`) never
does this -- its `overall` is strictly
`skill_score*0.55 + semantic_score*0.20 + experience_score*0.25`, and
ontology only powers the "related skills detected" explainability text,
never the ranking score. That extra term has been removed so every number
below is the score the live app actually produces. Ranking metrics barely
moved (relative order of candidates was mostly unaffected); the
skill-score ablation delta strengthened (see section 3) since it's no
longer being partly masked by the ontology bonus.

## 1. Full evaluation (`python research/full_evaluation.py`)

Dataset: 30 resumes x 10 jobs (300 labelled pairs). K=10, classification
threshold = score >= 70.

| Model | P@10 | R@10 | MRR | nDCG@10 | Precision | Recall | F1 |
|---|---|---|---|---|---|---|---|
| Baseline 1: Keyword | 0.820 | 0.908 | 1.000 | 0.965 | 1.000 | 0.467 | 0.637 |
| Baseline 2: TF-IDF + cosine | 0.640 | 0.736 | 1.000 | 0.829 | 1.000 | 0.663 | 0.797 |
| Baseline 3: SBERT | skipped -- `sentence-transformers` not installed in this environment | | | | | | |
| **RecruitSmart Hybrid** | **0.860** | **0.949** | 1.000 | **0.993** | 1.000 | 0.576 | 0.731 |

Machine-readable copy: `research/data/full_evaluation_results.json`.

Reading this table honestly: on *this* synthetic dataset the hybrid model
has the best ranking metrics (P@10, R@10, nDCG@10) of the three runnable
models. MRR is tied at a perfect 1.000 across all models -- every job in
this synthetic set has a relevant resume ranked first by construction,
which is a sign the synthetic label generator doesn't stress-test MRR,
not a genuine finding. Classification recall is lower for the hybrid than
for TF-IDF alone at this specific threshold (70) -- a threshold effect,
not a ranking-quality problem (see the ranking metrics, which is what
recruitment matching actually cares about).

## 3. Ablation study (`python research/ablation_study.py`)

```
Dataset: 30 resumes x 10 jobs

Variant                          nDCG@10    delta vs full
--------------------------------------------------------
Full RecruitSmart                  0.993    --
Remove semantic matching           0.950    -0.043
Remove skill ontology              0.993    +0.000
Remove experience score            1.000    +0.007
Remove skill score                 0.841    -0.152
```

Reading this honestly: skill-score is the dominant contributor (removing
it costs the most, -0.152), semantic matching also pulls real weight
(-0.043). "Remove skill ontology" shows exactly 0.000 **by construction,
not by finding**: the live app never adds ontology into the ranking score
in the first place (see the correctness-fix note above) -- ontology is an
explainability feature, not a ranking feature, in the current live
weighting. State that as a design fact in the paper, not as "ontology's
contribution wasn't measurable." Removing experience score *improving*
the metric slightly is a genuine (if small) finding on this dataset,
worth a sentence acknowledging it rather than omitting the row.

## 4. Fairness audit (`python research/fairness_test.py`)

```
Fairness audit over 30 base resumes x 10 jobs (60 name-variant resumes)

Demographic parity difference (threshold=70): 0.0000
Equal opportunity difference (threshold=70): 0.0000

Paired score gap (Group B minus Group A, same skills/experience/education):
  n=300  mean=+0.000  stdev=0.000  t-statistic=None
```

Reading this honestly: a paired gap of exactly 0.000 with 0 stdev across
300 pairs (t-statistic undefined -- no variance to test) means the name
substitution in this synthetic dataset produced literally zero score
change, every single time. That is a stronger, flatter result than a real
audit on real resumes would typically produce -- a sign the matcher
genuinely never looks at candidate names (there's nothing textual for
this probe to catch), not proof the system is broadly fair. Report this
as "no evidence of name-based sensitivity on this synthetic probe," not
as "bias-free."

## 5. Statistical significance (`python research/significance_report.py`) — NEW

Bootstrap 95% CIs (5000 resamples) on mean nDCG@10 across the 10 jobs,
plus a paired Hybrid-vs-baseline comparison (bootstrap p-value, Wilcoxon
signed-rank p-value, Cohen's d effect size):

| Model | mean nDCG@10 | 95% CI |
|---|---|---|
| Keyword | 0.965 | [0.928, 1.000] |
| TF-IDF + cosine | 0.829 | [0.748, 0.907] |
| **RecruitSmart Hybrid** | **0.993** | [0.979, 1.000] |

| Hybrid vs. | mean diff | 95% CI of diff | bootstrap p | Wilcoxon p | Cohen's d | effect size |
|---|---|---|---|---|---|---|
| Keyword | +0.028 | [0.000, 0.057] | 0.0622 | 0.2500 | 0.59 | medium |
| TF-IDF + cosine | +0.164 | [0.083, 0.247] | 0.0002 | 0.0156 | 1.14 | large |

Machine-readable copy: `research/data/significance_results.json`.

Reading this honestly: the hybrid's advantage over TF-IDF is both large
(Cohen's d = 1.14) and statistically significant by both tests
(p < 0.05). The advantage over the keyword baseline is a medium effect
(d = 0.59) but does **not** clear conventional significance with only 10
jobs (bootstrap p = 0.062, just above 0.05) -- report that honestly as
"a positive but not conclusively significant improvement over the keyword
baseline at this sample size," not as a confirmed win. This is exactly
the kind of caveat real evaluation results need, and exactly why more
labelled jobs (from real annotators) will matter: wider real data narrows
these intervals.

## 7. Bringing in real human-labelled data — NEW (`research/real_data_tools.py`)

Three subcommands, replacing the "you're on your own for this part" gap:

```bash
# 1. Generate a blank annotation sheet for your annotators to fill in
#    (samples pairs if the full cross-product is too large to hand-label)
python research/real_data_tools.py template --data-dir research/data \
    --out research/data/annotation_template.csv --max-pairs 300

# 2. (Optional but recommended) if two annotators double-label a subset,
#    measure inter-annotator agreement
python research/real_data_tools.py agreement \
    --file-a annotator1.csv --file-b annotator2.csv

# 3. Install the completed file as the real labels.csv -- this also
#    rewrites dataset_metadata.json to label_source: "human", which
#    flips every script's provenance banner from a warning to
#    "these numbers ARE citable"
python research/real_data_tools.py finalize \
    --labels-file completed_annotations.csv \
    --annotators "Name 1, Name 2" --agreement 0.81
```

After `finalize`, re-run every script in sections 1-6 unchanged -- same
commands, now against real data, now citable. `real_data_tools.py`
validates the file first (every row filled in, values are 0/1 only) and
backs up the previous `labels.csv` before overwriting.
